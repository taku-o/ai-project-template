# prevent-cc-sdd-auto-progress

## このスキルの目的（なぜ必要か）

cc-sdd（kiro）のスペック駆動開発は、**各工程の間に人間の承認ゲートを置く**ことで品質を担保する仕組みです。要件定義 → 設計 → タスク → 実装、という流れの各段階で、ユーザーが内容を確認し、明示的に承認してから次へ進みます。

ところが Claude には「ユーザーの役に立とう」として工程を先回りで進めてしまう傾向があります。具体的には次の2つです。

1. ユーザーが承認していないのに、`spec.json` の `approved` を `true` にして「承認済み」にしてしまう
2. ユーザーが作成を指示していないのに、次の文書（requirements.md / design.md / tasks.md）を勝手に生成してしまう

これらは一見「親切」ですが、**人間のレビューゲートを無効化する**ため、スペック駆動開発の根幹を壊します。このスキルは、その先走りを検知して止めるためのガードレールです。

## いつ発動するか

`.kiro/specs/<feature>/` 配下で、次のいずれかをしようとした時に発動します。

- `spec.json` の `approvals.requirements` / `approvals.design` / `approvals.tasks` の `approved` を `true` に変更しようとする時（その他の方法で「承認済み」を記録しようとする時も含む）
- `requirements.md` / `design.md` / `tasks.md` を**新規に作成**しようとする時（まだファイルが存在しない状態から作り出す時）

なお、**既にあるファイルへの編集・修正は、このスキルの対象外**です。ユーザーのフィードバック反映による通常の編集や、既存文書の再生成・上書きは止めません。止める対象はあくまで「存在しない文書を新規に作り出す」ケースに限ります。

## 守るべきルール

### ルール1: 承認は、ユーザーの明示的な承認がある時だけ

`spec.json` の `approved` を `true` にする前に、**この会話の中でユーザーがその文書を明示的に承認したか**を確認してください。

明示的な承認がないなら、`spec.json` を編集してはいけません。**操作を止めて**、ユーザーに「この文書を承認してよいか」を確認してください。

「親切のために先に承認しておく」「流れ的にもう承認でよいだろう」といった自己判断での承認は、たとえ内容が良くても行ってはいけません。承認の判断はユーザーが行います。

### ルール2: 文書の新規作成は、ユーザーの明示的な作成指示がある時だけ

まだ存在しない `requirements.md` / `design.md` / `tasks.md` を新規作成する前に、**この会話の中でユーザーがその文書の作成を明示的に指示したか**を確認してください。

明示的な作成指示がないなら、文書を新規作成してはいけません。**作成作業を止めて**、ユーザーに「この文書を作成してよいか」を確認してください。

特に「一つ前の工程が終わったから、流れで次の文書も作っておこう」という先回りは禁止です。前工程の完了は、次工程に進む指示ではありません。

このルールは「新規作成」だけが対象です。既にあるファイルを編集・修正・上書きする操作は止めません。

## 「明示的」とは何か

次のいずれかがあれば「明示的」とみなしてよい、と考えてください。

**承認の場合（ルール1）**
- ユーザーがその文書について「承認する」「approve」「OK、これで承認」など、承認の意思をはっきり示している
- ユーザーが承認用コマンド（`/kiro-approve-req`、`/kiro-approve-design`、`/kiro-approve-tasks` など）を実行した

**作成の場合（ルール2）**
- ユーザーが「要件定義書を作って」「設計書を作成して」「タスクリストを生成して」など、その文書の作成をはっきり指示している
- ユーザーがその文書を生成するコマンド/スキル（`/kiro-spec-requirements`、`/kiro-spec-design`、`/kiro-spec-tasks`、`/kiro-spec-init` など）を実行した

逆に、次のようなものは「明示的」とはみなしません。判断に迷ったら止めてユーザーに確認してください。
- 「いい感じだね」「ありがとう」などの肯定・お礼（承認の意思とは限らない）
- 「次に進めて」のような曖昧な指示で、どの文書を指すか／作成なのか承認なのかが特定できないもの
- ユーザーが何も言っていないのに Claude が流れから推測した「たぶん承認/作成してよいだろう」

## 例外: コマンド/スキルに組み込まれた処理は止めない

ユーザーがコマンドやスキルを実行し、**そのコマンド/スキルの定義に従って**承認や文書作成の処理が走る場合は、止めずにそのまま実行してかまいません。コマンド/スキルの実行そのものが、ユーザーの明示的な指示だからです。

例えば cc-sdd のスキルには、設計書を生成する時に一つ前の要件定義を `approved: true` にする、`-y`（auto-approve）フラグで承認を自動化する、といった処理が組み込まれています。これらはスキルの仕様どおりの動作なので、このガードレールの対象外です。

このスキルが止めるのはあくまで、**そうしたコマンド/スキルの外で、Claude が自分の判断で**承認状況を変えたり文書を作ったりするケースです。

## 止める時の対応

ルール1・ルール2に反する操作をしようとしていることに気づいたら、その操作（spec.json の編集、文書の Write）を**実行せずに中断**し、ユーザーに次を伝えてください。

- 何をしようとしていたか（例: design.md を新規作成しようとした／requirements の approved を true にしようとした）
- なぜ止めたか（ユーザーからの明示的な作成指示／承認がまだないため）
- どうしてほしいか（その文書を作成／承認してよいか、ユーザーの指示を求める）

問題を「無視して進める」「とりあえず作っておく」といった対応はしないでください。ユーザーの指示を待つことが正しい対応です。
